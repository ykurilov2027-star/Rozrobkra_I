# Перевірка помічника на наборі питань

Помічник, який гарно відповів на два питання під час демонстрації, — це ще
не помічник. Тут ви проганяєте набір питань із відомими відповідями через
весь конвеєр і для кожної невдачі зʼясовуєте, **чий це промах — пошуку чи
моделі**. Без цього поділу невідомо, що лагодити: індекс чи інструкцію.

## Що зробити

У прикладі вже є 13 сценаріїв. За потреби скопіюйте його у `questions.json`,
доповніть власними питаннями та запустіть із кореня проєкту:

```bash
python eval/run_eval.py
```

Скрипт зберігає детальний `eval/report.json`: контекст, позиції очікуваних
документів, цитати, відповідь, часи, usage і класифікацію помилок. Він
перевіряє наявність 12–15 питань. Для порівняння збережіть окремі звіти:

```bash
python eval/run_eval.py --label baseline --report eval/report-baseline.json
# Той самий набір, змінено тільки ліміт контексту з 4 до 5:
python eval/run_eval.py --context-chunks 5 --label context-5 --report eval/report-context-5.json
```

Фактологічний збіг у зведенні оцінюється простим регістронезалежним пошуком
очікуваної фрази у відповіді. Це лише попередня автоматична перевірка:
перегляньте контекст, відповідь і процитовані фрагменти вручну перед
висновками. Звіт не замінює перевірку, чи кожен факт справді підтриманий
саме процитованим джерелом.

`очікувані_документи` — документи, що містять відповідь. Якщо документ
релевантний, але потрібного факту в ньому немає, задайте окремо
`очікувані_документи_в_контексті`.

1. Скопіюйте `questions.example.json` у `questions.json` і доповніть його
   до 12–15 питань. Види питань — у прикладі; додайте свої, зокрема
   питання з фільтром за товаром (розділ про скидання є в усіх чотирьох
   інструкціях), питання іншою мовою і те, на якому ваш помічник, за
   вашим передчуттям, спіткнеться.
2. Для кожного питання вкажіть **очікувані документи** — файли з `docs/`,
   у яких є відповідь, — **факти**, які має містити правильна відповідь, і
   чи **очікується відповідь** узагалі. Для питань поза базою та для тих,
   відповідь на які клієнтові давати не можна, — порожній список і `false`.
3. Прожене весь набір через конвеєр. Зафіксуйте для кожного питання те, що
   перелічено нижче, — і **збережіть контекст**, який бачила модель: без
   нього не розібрати, де сталася помилка.
4. Змініть **одну** річ — кількість фрагментів у контексті, їхній порядок,
   формулювання інструкції, поріг, спосіб пошуку — і прожене набір ще раз.
   Змінюйте за раз щось одне.
5. Запишіть висновки у `findings.md`.

Для порівняння оцінюйте обидва звіти за однаковим набором питань і
конфігурацією, за винятком заявленої єдиної зміни. Не записуйте висновки
до запуску експерименту: runner потребує локального індексу та доступного
LLM-провайдера.

Як проганяти — ваше рішення: вручну через сторінку або окремим скриптом,
що викликає `rag.answer` без веб-рівня. Другий варіант заощадить час і
гроші: набір проганяється щонайменше двічі, кожне питання — виклик моделі.

## Що фіксувати

Для кожного питання — окремо про пошук і окремо про модель:

| Етап | Що | Навіщо |
|---|---|---|
| пошук | чи очікуваний документ **серед фрагментів, переданих моделі** (не в top-k пошуку — саме в контексті), і на якій позиції | якби модель була ідеальною — чи мала б вона з чого відповісти |
| пошук | що ще потрапило в контекст: архівна редакція, внутрішній документ, сторонні фрагменти | зайве в контексті — теж помилка пошуку, навіть якщо модель на неї не повелася |
| модель | чи відповідь містить очікувані факти і не містить чужих | правильність |
| модель | чи все у відповіді є в контексті — кожне число, строк, умова | ґрунтованість: відповідь може бути правильною «з голови» — і це теж провал |
| модель | чи джерела, на які послалася модель, справді містять те, що вона сказала | посилання — не прикраса, а те, що клієнт може перевірити |
| модель | для питань без відповіді — чи сказала «у базі знань немає»; для питань із відповіддю — чи не відмовилася безпідставно | контрольована поведінка в обидва боки |
| обидва | токени запиту й відповіді, час пошуку, час генерації | ціна питання: скільки з неї — контекст |

Зведіть по всьому набору: частку питань, де очікуваний документ був у
контексті; частку правильних відповідей; скільки разів помічник відповів
там, де мав відмовити, і відмовив там, де мав відповісти; скільки разів
посилання на джерела були хибними.

## Класифікація помилок

Кожну невдачу віднесіть до одного з типів. Спершу дивіться в контекст:
**якщо правильна відповідь у ньому була — помилка моделі; не було —
помилка пошуку.**

| Етап | Тип | Приклад |
|---|---|---|
| пошук | не знайдено | потрібного фрагмента в контексті немає |
| пошук | не та редакція | в контексті архівні правила доставки — з фільтром чи без |
| пошук | витік | внутрішній документ потрапив у контекст для питання клієнта |
| пошук | розрізаний факт | межа фрагмента розділила умову й число |
| пошук | шум | потрібний фрагмент є, але серед пʼяти сторонніх |
| модель | вигадка при правильному контексті | контекст містить «14 днів», відповідь — «30 днів» |
| модель | відповідь «з голови» | контекст порожній або не про те, а відповідь є — правдоподібна, але не з бази |
| модель | змішування фрагментів | суму з архівної редакції поєднано з умовою з чинної |
| модель | хибне посилання | названо джерело, у якому сказаного немає, або джерело, якого не показували |
| модель | безпідставна відмова | відповідь у контексті є, модель каже, що немає |
| модель | виконала вказівку з питання | питання попросило змінити роль або розкрити те, чого немає в контексті |

Останній стовпець вашої таблиці — **що у вашому рішенні цю помилку ловить
або не пускає**: фільтр у коді, поріг, інструкція, перевірка посилань.
Порожня клітинка в цьому стовпці — і є висновок.

## Що написати у висновках

Не переказ таблиць, а відповіді на питання:

- Скільки невдач — на боці пошуку і скільки — на боці моделі? Що з цього
  випливає для того, що лагодити першим?
- Чи відрізняється поведінка на питаннях без відповіді від поведінки на
  питаннях із відповіддю? Хто це забезпечив — поріг у коді, інструкція чи
  обоє? Що буває, коли лишити лише одне з них?
- Чи довіряєте ви полю «відповідь знайдено», яке заповнила модель? На яких
  питаннях воно розійшлося з вашою перевіркою?
- Що змінила ваша одна зміна (крок 4)? У який бік, на яких питаннях, і
  скільки це коштує в токенах?
- Що ви взяли б у застосунок, який відповідає клієнтам: за яких умов
  відповідь показується як є, коли — з позначкою «перевірте у джерелі», а
  коли передається оператору?

`questions.json` і `findings.md` до репозиторію не потрапляють — вони ваші.
